# Contour D — scroll-zoom jank fix (630409186)

Scope: `assets/contour/board/hero.js`, `assets/contour/board/hero.css`. `variants/d.html` untouched.
No visual change: HAND_P0 = 0.30, S0 = 0.42, easing, thresholds, board chrome/claim/copy and SITE-COPY strings are as before.

## Causes (all in the per-scroll RAF: `update()` → `handoff()` → `draw()`)

1. **Forced layout every frame.** `hero.offsetHeight`, `hero.getBoundingClientRect()`, `main.offsetTop` and `hero.offsetTop` were read every frame, *after* the same frame had written `textContent`/opacity, so each read forced a synchronous reflow of the page.
2. **JS pin racing the threaded scroll.** `#main` was held at the viewport top with `translateY(-(main.offsetTop - scrollY))`. The compositor scrolls `#main` up immediately and the main thread puts it back one RAF later, so any slow frame shows as `#main` shaking/lagging during the handoff (on top of the subpixel wobble from fractional values).
3. **Full-screen WebGL redraw on every scroll event, page-wide.** `draw()` ran `drawArrays` (DPR-2 full-screen fragment shader) for every scroll frame on the whole page, including after the hero is gone, and set the canvas size, viewport and uniforms each time.
4. **Unconditional DOM writes.** `.inv` clip-path, 14 `.fade` opacities, ALT/contour text nodes and `#main`/stage styles were written every frame even when unchanged.

## Changes

- **Cached metrics** (`measure()` / `relayout()`): `vh`, `heroTop`, `run`, `endY` (= `#main` offsetTop, measured unpinned), `dpr`, canvas size, `uRes`/`uDpr`. Re-measured on `resize`, `fonts.ready`, reduced-motion change and a `ResizeObserver` on `#hero` + `#main` (late images, `<details>`). `update()` now only reads `scrollY`; progress is `(scrollY - heroTop) / run`, the same as `-rect.top / run`.
- **Compositor-side pin:** while handing, `#main.handoff` is `position: sticky; bottom: var(--pin)` with `--pin = innerHeight - #main height`. That holds `#main`'s top at the viewport top exactly while its natural top is below it (`nat > 0`), and has no effect once `nat ≤ 0`. That is the same range the old `translateY(-nat)` covered, but now the compositor applies it in sync with the scroll. Sticky doesn't affect flow, so page height and scroll range are unchanged. `focusin` uses the cached `endY`, because `offsetTop` includes the sticky offset.
- **Scale about the hole** as one write: `transform-origin: 0 0` (CSS) plus `translate3d(hx(1-s), hy(1-s), 0) scale(s)`. This is mathematically the same as the old `origin hx hy; translateY(-nat) scale(s)` once pinned. The hole centre is rounded to 0.1px and used for both the transform and the circle clip, translate is rounded to 0.01px and scale to 1e-4, so the strings are stable.
- **Write-on-change:** `#main` transform / clip-path / opacity, stage opacity, `.fade` opacity (3 dp), ALT and `(NN)` contour text, and the `.inv` D clip path are written only when the formatted string changes.
- **WebGL draw skip:** `drawArrays` and the clip-path update are skipped when `view.cx/cy/R` moved < 0.005px since the last draw (below `dPath`'s 0.01px rounding). Resize/fonts force a redraw. DPR cap stays at 2 (no quality change).
- **GPU hint:** `#hero.handing .board-stage { will-change: opacity }` only during the handoff, so the stage dissolve is a compositor opacity change. The first fold (p = 0) is untouched, so the board pixel gate is unaffected.
- Reduced motion: unchanged path (p = 0, no handoff, no sticky).

## Verification (headless Chrome, local, original vs patched)

- Pixel diff at p = 0, .1, .25, .3, .35, .45 … .995, 1, past-end, at 1280×800@1x and 390×844@2x, motion and reduced motion:
  - Identical outside the handoff (max channel diff ≤ 3).
  - During the handoff, the best alignment is offset 0,0 and the mean diff is < 0.7/255. The only differences are ≤ 1-device-px glyph rasterization: the old pin used the integer-rounded `offsetTop`, while sticky is exact.
- 240-frame scripted scroll through the runway at 1280×800: layout passes 261 → 135 and main-thread task time −22%. Frame times in headless are dominated by software WebGL (SwiftShader), so they aren't a valid fps figure. Check fps on real hardware.
- `drawArrays` calls on 60 scroll steps below the fold: 61 → 0. In the runway: 60 → 60, one per real view change.
- Resize mid-handoff keeps `#main` pinned, `endY` is re-measured correctly, keyboard focus into `#main` mid-flight still jumps to the end, and there are no page errors.

## Not changed / follow-ups

- `assets/site.js` has its own scroll RAF that reads `getBoundingClientRect` on `[data-theme=dark]` sections and nav targets, plus `#hero.offsetHeight`, after writing. That is out of scope here and is a candidate for the same caching treatment.
- `#main.handoff` still promotes `#main` (`will-change: transform`) at handoff start, as before. Chrome may raster it at the initial 0.42 scale until the class drops at the end, which is the same as the shipped behaviour.
